Abstract

This specification defines an API that lets web applications share musical tempo, beat grid, phase, and start/stop transport state with other applications and devices on the local network, so that they play in time together.

1. Introduction

Web applications for music making, live performance, and music education need to play in time with other software and instruments in the same room: a DAW on a laptop, a groovebox, an app on a phone, another browser tab.

This specification defines how a web application joins a shared musical timeline. The user agent finds the other participants on the local network, keeps its clock in step with theirs, and carries the network traffic. Web applications see only the timeline: they capture snapshots of it to schedule audio and visuals, and commit changes to it, such as a new tempo or starting the transport.

This specification does not define a network protocol. A user agent takes part in tempo sessions using one or more tempo sync protocols of its choosing.

2. Concepts

2.1. Sessions and participants

A tempo session is a musical timeline shared by every application taking part in it, together with its start/stop state.

A tempo sync protocol is an implementation-defined network protocol by which applications on a local network find each other and agree on a tempo session.

A participant is anything taking part in the tempo session: an application or device on the local network, or a document in this user agent that has an open TempoSession.

A user agent takes part in the network as a single participant, however many of its documents have sessions open. Its documents share that one endpoint and see changes made by each other immediately.

A TempoSession has other participants when the tempo session includes any participant other than that TempoSession itself: another application or device on the network, or another TempoSession in this user agent.

2.2. Timelines, beats, and tempo

A timeline maps points in continuous time to continuous musical beat coordinates.

Tempo is the rate of musical progress, measured in beats per minute (BPM). Tempo is a positive number.

A beat is a number indicating musical position. Integer values are whole beats, such as quarter notes in common time, and fractions are subdivisions of a beat.

A timeline is a tempo together with a time origin t0 and the beat origin b0 at that time. The relationship between time t and beat b is:

b(t)=b0+(t−t0)×tempo60 t(b)=t0+(b−b0)×60tempo

The tempo session’s timeline is the shared timeline.

2.3. Quantum and phase

The quantum is the number of beats in a recurring musical unit, usually a bar. For example, a bar of 4/4 has a quantum of 4, and a bar of 3/4 has a quantum of 3.

The phase of a beat b for a quantum q is its position within that unit, in the half-open interval [0,q):

phase(b,q)=(bmodq+q)modq

Participants share phase, not beat numbers. Two participants using the same quantum agree on where every bar starts, but one may call a bar line beat 0 while another calls it beat 64. Each TempoSession has its own beat offset, the difference between its beat numbering and the shared timeline’s. A beat offset only changes a session’s numbering, never the shared timeline, so other participants never see it.

For a quantum q, a session numbers beats using its beat offset o rounded to the nearest multiple of q, so that its beats keep the shared phase for that quantum:

offsetq=q×round(oq)

where round(x) is the integer nearest to x, choosing the greater one when two are equally near.

The phase-sharing model lets a page start its own pattern at "beat 0" on the next bar line without moving anyone else’s bar lines. Beat numbering only has to agree within a page, so participants never need to negotiate it.

2.4. Time bases

The user agent keeps the shared timeline on a monotonic system host time clock. Applications see times in one of two time bases, in seconds:

  1. The current high resolution time of the relevant global object: performance.now() divided by 1000. This suits visuals and timers.

  2. An AudioContext’s currentTime, the time base of audio rendering for that context.

Each TempoSessionState records the time base it was captured in. All of its times use that time base.

Mapping between host time and an audio context’s time involves an estimate. The audio device’s clock drifts relative to the host clock, and output buffering delays when a rendered sample reaches the speakers. The user agent SHOULD map to the time at which audio reaches the output (the same correspondence as getOutputTimestamp()), and SHOULD smooth that mapping so that consecutive captures don’t jitter.

3. Navigator extension

[SecureContext]
partial interface Navigator {
  readonly attribute TempoSync tempoSync;
};

The tempoSync attribute returns the TempoSync instance associated with the current document.

4. Interface TempoSync

[SecureContext, Exposed=Window]
interface TempoSync {
  Promise<TempoSession> requestSession(optional TempoSessionOptions options = {});
};

dictionary TempoSessionOptions {
  double quantum = 4;
};

The TempoSync interface is the entry point for joining a tempo session.

4.1. Methods

When the requestSession(options) method is invoked, the user agent MUST run these steps:

  1. Let promise be a new promise.

  2. Let document be the current document.

  3. If document is not a secure context, reject promise with a "SecurityError" DOMException and return promise.

  4. If document is not allowed to use the policy-controlled feature "tempo-sync", reject promise with a "SecurityError" DOMException and return promise.

  5. If options["quantum"] is less than or equal to 0, reject promise with a RangeError and return promise.

  6. Run the following steps in parallel:

    1. Let permission be the result of requesting permission to use "tempo-sync".

    2. If permission is not "granted", reject promise with a "NotAllowedError" DOMException and abort these steps.

    3. If the user agent is not already taking part in a tempo session, join or start one using its tempo sync protocols.

    4. Let session be a new TempoSession whose quantum is options["quantum"] and whose beat offset is 0.

    5. Resolve promise with session.

  7. Return promise.

5. Interface TempoSession

[SecureContext, Exposed=Window]
interface TempoSession : EventTarget {
  readonly attribute boolean hasPeers;
  readonly attribute double quantum;
  TempoSessionState captureState(optional BaseAudioContext context);
  undefined commitState(TempoSessionState state);
  undefined close();
  attribute EventHandler onpeerschange;
  attribute EventHandler ontimelinechange;
  attribute EventHandler onplayingchange;
};

A TempoSession object is a document’s connection to the tempo session.

5.1. Attributes

  • hasPeers: Returns true if this session has other participants, and false otherwise.

  • quantum: Returns the quantum the session was created with. Methods of TempoSessionState use it when their quantum argument is omitted.

  • onpeerschange: Event handler for the peerschange event, fired when hasPeers changes.

  • ontimelinechange: Event handler for the timelinechange event, fired when the shared timeline changes: its tempo, or where its beats fall.

  • onplayingchange: Event handler for the playingchange event, fired when the shared start/stop state changes.

When the shared timeline, the shared start/stop state, or the result of has other participants changes for an open TempoSession, whatever caused the change, the user agent MUST queue a global task on the relevant global object of that TempoSession to fire an event named timelinechange, playingchange or peerschange respectively at it.

A snapshot stays correct until one of these events fires, because a timeline is linear. Applications that hand snapshots to a worker or an AudioWorkletProcessor can capture and post a new one when these events fire, rather than on every frame.

5.2. Methods

When the captureState(context) method is invoked, the user agent MUST run these steps:

  1. If this TempoSession is closed, throw an "InvalidStateError" DOMException.

  2. Let shared be the current shared timeline and startStop the current shared start/stop state, both in host time.

  3. If context was given, let timeBase be context’s time base. Otherwise let timeBase be the current high resolution time of this TempoSession’s relevant global object.

  4. Let state be a new TempoSessionState with:

    • session: this TempoSession.

    • time base: timeBase.

    • tempo, time origin and beat origin: shared’s, with its time origin mapped from host time into timeBase.

    • beat offset: this TempoSession’s beat offset.

    • default quantum: this TempoSession’s quantum.

    • playing: whether startStop is playing.

    • playing time: the time startStop last changed, mapped from host time into timeBase.

    • solo: true if this TempoSession does not have other participants, and false otherwise.

  5. Return state.

When the commitState(state) method is invoked, the user agent MUST run these steps:

  1. If this TempoSession is closed, throw an "InvalidStateError" DOMException.

  2. If state’s session is not this TempoSession, throw an "InvalidModificationError" DOMException.

  3. If state’s committed flag is set, throw an "InvalidStateError" DOMException.

  4. Set state’s committed flag.

  5. Set this TempoSession’s beat offset to state’s beat offset.

  6. If state’s timeline changed flag is set, set the shared timeline to state’s tempo, time origin and beat origin, mapping the time origin from state’s time base into host time.

  7. If state’s playing changed flag is set, set the shared start/stop state to state’s playing at its playing time, mapped into host time.

  8. If either flag was set, share the change with the other participants, subject to rate limits.

Only the parts of a state that the application changed are committed. Committing a state captured before another participant changed the tempo does not undo that change, unless the application also changed the tempo.

When the close() method is invoked, the user agent MUST run these steps:

  1. If this TempoSession is already closed, return.

  2. Mark this TempoSession as closed.

  3. If no other open TempoSession remains in the user agent, the user agent SHOULD leave the tempo session.

6. Interface TempoSessionState

[SecureContext, Exposed=(Window,Worker,AudioWorklet), Serializable]
interface TempoSessionState {
  readonly attribute double tempo;
  undefined setTempo(double bpm, double atTime);
  double beatAtTime(double time, optional double quantum);
  double phaseAtTime(double time, optional double quantum);
  double timeAtBeat(double beat, optional double quantum);
  undefined requestBeatAtTime(double beat, double time, optional double quantum);
  undefined forceBeatAtTime(double beat, double time, optional double quantum);
  readonly attribute boolean isPlaying;
  readonly attribute double timeForIsPlaying;
  undefined setIsPlaying(boolean playing, double atTime);
};

A TempoSessionState is a snapshot of the tempo session, taken by captureState(). Its methods only read and change the snapshot; nothing reaches the session until it is passed to commitState(). It is a serializable object, so an application can post it to a worker or an AudioWorkletProcessor, use it there, and post it back to be committed.

6.1. Internal slots

A TempoSessionState has these internal slots:

  • session: the TempoSession that captured it.

  • time base: the time base its times are in (see § 2.4 Time bases).

  • tempo, time origin and beat origin: the shared timeline’s tempo, time origin and beat origin, with times in its time base.

  • beat offset: the session’s beat offset.

  • default quantum: the quantum used when a method’s quantum argument is omitted.

  • playing and playing time: the shared start/stop state and the time it last changed.

  • solo: whether the session had no other participants when the state was captured.

  • timeline changed, playing changed and committed flags, initially unset.

To find the shared beat of a state at a time, apply the timeline relationship from § 2.2 Timelines, beats, and tempo to its tempo, time origin and beat origin.

To find the offset for a quantum q, round the state’s beat offset to a multiple of q as in § 2.3 Quantum and phase.

The effective quantum for a method’s quantum argument is that argument if it was given and is greater than 0, and the state’s default quantum otherwise.

6.2. Serialization

The serialization steps of a TempoSessionState, given value, serialized and forStorage, are:

  1. If forStorage is true, throw a "DataCloneError" DOMException.

  2. Set serialized’s fields to value’s internal slots, except that times in a time base that is a current high resolution time are first mapped into host time, and the session is stored as an identifier for that TempoSession.

The deserialization steps, given serialized, value and targetRealm, are:

  1. Set value’s internal slots from serialized’s fields.

  2. If the times were mapped into host time, map them into the current high resolution time of targetRealm’s global object, and make that value’s time base. Times in an audio context’s time base stay as they are: AudioWorkletGlobalScope’s currentTime is the same clock.

  3. Set value’s session to the TempoSession that the identifier refers to.

So a state captured with no audio context and posted to a worker reads in the worker’s performance.now(). A state captured with an AudioContext and posted to that context’s AudioWorkletProcessor reads in its currentTime. A state posted back to the document can be committed.

6.3. Attributes

  • tempo: Returns the state’s tempo, in beats per minute.

  • isPlaying: Returns the state’s playing.

  • timeForIsPlaying: Returns the state’s playing time.

6.4. Methods

Every argument these methods take is a double, which WebIDL restricts to finite values: a NaN or infinite argument throws a TypeError before any of the steps below run, so the steps don’t check for one again. The same holds for quantum.

When beatAtTime(time, quantum) is invoked, the user agent MUST run these steps:

  1. Let q be the effective quantum for quantum.

  2. Return the beat: the shared beat at time plus the offset for q.

When timeAtBeat(beat, quantum) is invoked, the user agent MUST run these steps:

  1. Let q be the effective quantum for quantum.

  2. Return the time at which the shared beat is beat minus the offset for q.

When phaseAtTime(time, quantum) is invoked, the user agent MUST run these steps:

  1. Let q be the effective quantum for quantum.

  2. Return the phase of the shared beat at time for q.

This equals the phase of beatAtTime(time, quantum), since the offset for q is a multiple of q. Every participant using the same quantum sees the same phase.

When setTempo(bpm, atTime) is invoked, the user agent MUST run these steps:

  1. If bpm is less than or equal to 0, throw a RangeError.

  2. Let b be the shared beat at atTime.

  3. Set the state’s time origin to atTime, its beat origin to b, and its tempo to bpm.

  4. Set the state’s timeline changed flag.

When requestBeatAtTime(beat, time, quantum) is invoked, the user agent MUST run these steps:

  1. Let q be the effective quantum for quantum.

  2. If the state is solo, invoke forceBeatAtTime() with beat, time and q, and return.

  3. Let current be the result of invoking beatAtTime() with time and q.

  4. Let launch be the smallest number greater than or equal to current that has the same phase as beat for q.

  5. Let launchTime be the result of invoking timeAtBeat() with launch and q.

  6. Set the state’s beat offset to beat minus the shared beat at launchTime.

With other participants present, this waits for the next point at or after time where the session’s phase matches beat’s, and numbers that point beat. It changes only this session’s beat numbering, so no one else’s bar lines move. Alone, the application can have beat exactly at time.

When forceBeatAtTime(beat, time, quantum) is invoked, the user agent MUST run these steps:

  1. Let q be the effective quantum for quantum.

  2. Let current be the shared beat at time.

  3. Let shift be the number in the interval (−q2,q2] such that current + shift has the same phase as beat for q.

  4. Set the state’s time origin to time and its beat origin to current + shift.

  5. Set the state’s beat offset to beat − (current + shift).

  6. Set the state’s timeline changed flag.

This moves the session’s bar lines, by up to half a quantum, for every participant. It is for an application that must put a beat at an exact time, such as a sequencer following an external clock. Applications that only want to start in time should use requestBeatAtTime().

When setIsPlaying(playing, atTime) is invoked, the user agent MUST run these steps:

  1. Set the state’s playing to playing and its playing time to atTime.

  2. Set the state’s playing changed flag.

7. Permissions and policy integration

7.1. Permissions Policy

This specification defines a policy-controlled feature identified by the string "tempo-sync".

The default allowlist is 'self'.

An iframe document cannot call requestSession() unless allowed by its container policy:

<iframe src="https://synth.example.com" allow="tempo-sync"></iframe>

7.2. Permissions API

This specification defines a powerful feature whose name is "tempo-sync".

  • When granted, requestSession() succeeds without prompting.

  • When denied, requestSession() immediately rejects with a "NotAllowedError" DOMException.

  • When in prompt state, the user agent prompts the user with the origin of the document.

8. Security and privacy considerations

8.1. Local network presence

Joining a tempo session sends traffic on the local network, and the session reveals whether anyone else is taking part. A page could use that to learn that music software or equipment is present.

Mitigations:

  1. Permission: The user agent MUST obtain permission before sending any local network traffic for a session. The prompt should say that the site will be able to tell whether music apps or devices on the network are playing along.

  2. One bit of presence: Pages learn only hasPeers: whether anyone else is in the session. They learn nothing about how many participants there are or what they are, and no addresses, ports or device names. A user agent can show more, such as a count of devices, in its own interface.

  3. One participant per user agent: The user agent takes part in the network as one participant, so other devices cannot see how many documents have sessions open.

8.2. Cross-origin communication

Every document with an open session shares one timeline. A change committed by one origin is visible to every other origin with a session open, and hasPeers reveals whether any other session is open. Two cooperating origins that both hold the permission could use this to signal to each other. They could already signal through a device on the network, so this adds little, but user agents SHOULD NOT treat the session as an isolation boundary.

The API is restricted to secure contexts, and to top-level documents unless a container policy allows "tempo-sync".

8.3. Disruption and denial of service

A malicious or broken page could change the tempo or move the bar lines repeatedly, which would disrupt everyone playing, and could generate a flood of network traffic.

The user agent MUST rate-limit changes shared by commitState(). For example, it could share at most 20 changes per second and coalesce the rest. Changes that only affect a session’s own beat numbering are not shared and need no limit.

User agents SHOULD consider leaving the tempo session while no document with an open session is visible or playing audio.
